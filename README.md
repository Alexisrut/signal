# Система мониторинга сигналов

Fullstack-приложение: Node-сервер с SQL-хранилищем (SQLite), REST API, почтовой подсистемой,
фоновым процессом эскалации и серверным экспортом в Excel — и клиент на нативных ES-модулях.
Слой предметной области (`shared/`) физически один и тот же для сервера и браузера, поэтому
статусы, правила переходов и валидация не могут разойтись между клиентом и сервером.

## Запуск

```bash
cd signal-monitor && npm install && npm start
```

Приложение поднимется на `http://localhost:5175` (порт меняется переменной `PORT`).

**Первый администратор** создается при первом запуске, если в системе нет ни одной
учетной записи администратора. Логин, почта и пароль берутся из переменных
`DEFAULT_ADMIN_LOGIN`, `DEFAULT_ADMIN_EMAIL` и `DEFAULT_ADMIN_PASSWORD` (см. `.env.example`).
Если пароль не задан, подставляется демонстрационный — сервер предупредит об этом
при старте отдельной строкой. На открытом домене пароль задавать обязательно.

Подрядчик регистрируется сам: название компании, ФИО, почта и пароль. Название компании
одновременно служит логином. Учетные записи администраторов заводит только главный администратор.

### Почта

Настройки читаются из файла `.env` в корне проекта (он в `.gitignore`, шаблон — `.env.example`).
Переменные, заданные в самом окружении, перекрывают файл — так продакшен и секреты Codespaces
имеют приоритет над локальными значениями.

```bash
cp .env.example .env   # затем вписать пароль в SMTP_PASS
```

**Рабочая конфигурация для mail.ru:**

```ini
SMTP_HOST=smtp.mail.ru
SMTP_PORT=465
SMTP_SECURE=true
SMTP_USER=ящик@mail.ru
SMTP_PASS=пароль_для_внешних_приложений
MAIL_FROM=Мониторинг сигналов <ящик@mail.ru>
APP_URL=https://адрес-по-которому-открывают-приложение
```

Три места, где чаще всего ошибаются:

- **`SMTP_PASS` — это «пароль для внешних приложений»** из настроек ящика, а не тот, которым
  вы входите на сайт почты. С основным паролем mail.ru отвечает `535 Authentication failed`.
- **Адрес в `MAIL_FROM` обязан совпадать с `SMTP_USER`** — иначе письмо отклоняется на отправке.
  Если `MAIL_FROM` не задан, он собирается из `SMTP_USER` автоматически.
- **`APP_URL` должен быть тем адресом, по которому приложение реально открывают.** Он
  подставляется в ссылки внутри писем: при `localhost` в Codespaces ссылка подтверждения почты
  у получателя не откроется.

Порт 465 — SSL с первого байта, 587 — STARTTLS. Признак `secure` выводится из порта, если не
задан явно. При старте сервер проверяет авторизацию и печатает результат, ничего не отправляя:

```
SMTP smtp.mail.ru:465 — авторизация прошла, письма уходят с Мониторинг сигналов <ящик@mail.ru>
```

Если `SMTP_HOST` не задан, включается **dev-инбокс**: письмо всё равно собирается настоящим
MIME-сообщением, сохраняется в `data/mailbox/*.eml` и открывается по адресу `/dev/mailbox`.
При живом SMTP dev-инбокс автоматически отключается и отдает 404.

## Модель данных (SQL)

| Таблица | Назначение |
| --- | --- |
| `users` | подрядчики и администраторы: `login` (у подрядчика — название компании), `email`, `password_salt`/`password_hash`; у подрядчика — `company_name`/`full_name`, у администратора — `is_email_verified` и `categories` (JSON-массив видимых категорий) |
| `signals` | сигналы: сквозной номер, тема писем, автор, категория (`NULL` — не распределен), подрядчик, сектор, описание, статус, `distributed_at`, метки времени |
| `signal_history` | история событий: когда, из какого статуса, в какой, кем, с каким комментарием и действием |
| `files` | вложения: имя, MIME-тип, размер в байтах, URL и путь в хранилище |
| `attachments` | связь файлов с сигналом |
| `assignments` | исполнители: сущность ↔ пользователь ↔ момент принятия в работу |
| `email_tokens` | одноразовые токены подтверждения почты с TTL |
| `sessions` | сессии пользователей |
| `mail_log` | журнал отправленных писем (тема, получатель, способ доставки, ошибка) |

Анонимных пользователей нет: и подрядчик, и администратор работают только после входа по логину
и паролю. Гостю API отдает пустое состояние — ему доступны лишь вход и регистрация.

### Роли

| Роль | Что видит и может |
| --- | --- |
| `contractor` | только свои сигналы: создание, доработка по замечаниям входного контроля, комментарии, правка до закрытия, подтверждение выполнения или возврат на доработку |
| `admin` | сигналы **выданных ему категорий**: отчет о выполнении и направление на подтверждение, эскалация, правка, экспорт |
| `superadmin` | всё: раздел «Входной контроль», все категории, создание учетных записей и выдача категорий |

### Категории

| id | Название |
| --- | --- |
| `admin_finance` | Административный/финансовый |
| `design` | Проектирование |
| `supply` | Поставка |
| `other` | Разное |

Категорию **выбирает не подрядчик**. Новый сигнал создается со значением `NULL` и попадает
на входной контроль — в раздел «Входной контроль» (`#/admin/distribution`), видимый только
главному администратору. Пока сигнал не распределен, его не видит ни один обычный администратор
или руководитель.

## Конечный автомат статусов

```
     (создание)
         │
         ▼
   ┌──────────────────┐   вернуть на доработку    ┌──────────────────────┐
   │ ВХОДНОЙ КОНТРОЛЬ │ ────────────────────────► │ НА ДОРАБОТКЕ         │
   │  главный админ   │ ◄──────────────────────── │ У ПОДРЯДЧИКА         │
   └──────────────────┘  дополнен и отправлен     └──────────────────────┘
         │ распределить ответственному
         ▼
   ┌──────────┐   48 ч в работе: система или вручную   ┌─────────┐
   │ В РАБОТЕ │ ─────────────────────────────────────► │ КРАСНЫЙ │
   └──────────┘                                        └─────────┘
         │      отчет + «Направить на подтверждение»        │
         └────────────────────────┬─────────────────────────┘
                                  ▼
                 ┌──────────────────────────────────┐
                 │ ОЖИДАЕТ ПОДТВЕРЖДЕНИЯ ПОДРЯДЧИКА │ ◄─────────────┐
                 └──────────────────────────────────┘               │
                    │ подтвердил             │ вернул с комментарием │
                    ▼                        ▼                       │
               ┌─────────┐       ┌────────────────────────┐          │
               │ ЗАКРЫТ  │       │ ВОЗВРАЩЕН НА ДОРАБОТКУ │ ─────────┘
               └─────────┘       └────────────────────────┘  дополнил отчет
```

| Действие | Переход | Кто выполняет | Условие |
| --- | --- | --- | --- |
| создание | → На входном контроле | подрядчик или сотрудник | — |
| вернуть на доработку | входной контроль → доработка у подрядчика | главный администратор | обязательный комментарий, что дополнить |
| доработать | доработка → входной контроль | автор сигнала | правки, новые файлы или пояснение |
| распределить | входной контроль → В работе | главный администратор | категория и хотя бы один ответственный |
| эскалация | В работе / Возвращен → Красный | система **или** сотрудник | автоматически через 48 часов либо вручную |
| направить на подтверждение | В работе / Красный → Ожидает подтверждения | ответственный | отчет о выполнении |
| подтвердить выполнение | Ожидает подтверждения → Закрыт | автор сигнала | — |
| вернуть на доработку | Ожидает подтверждения → Возвращен на доработку | автор сигнала | обязательный комментарий |
| повторно направить | Возвращен → Ожидает подтверждения | ответственный | дополненный отчет |
| закрыть «решено» | любой открытый, кроме проверки → Закрыт | только автор | проблема решилась сама |
| отклонить | → Отклонен | только главный администратор | обязательная причина |
| возобновить | Закрыт/Отклонен → последний рабочий статус | сотрудник | — |

**Ответственный не закрывает сигнал сам**: он описывает в отчете, что сделано и какое решение
принято, и направляет результат подрядчику. Окончательно закрывает сигнал только сторона,
обозначившая проблему.

Срок 48 часов считается только по времени «В работе» (после возврата подрядчиком — заново
с момента возврата): входной контроль, доработка у подрядчика, проверка результата и закрытые
периоды в него не входят. У автоматической эскалации автор события — Система, у ручной —
конкретный сотрудник.

Правила описаны в `shared/state-machine.js` (`WORKFLOW`) и применяются на сервере до записи
в БД, поэтому запрет действует и для интерфейса, и для прямых запросов к API.

## Исполнители, правки и история событий

**Принятие в работу.** Администратор берет сигнал на себя — в карточке и на доске
появляется исполнитель. **Исполнителей может быть несколько**: занятость коллегой не мешает
принять тот же сигнал и себе, повторное принятие тем же человеком отклоняется. Снять исполнителя
(себя или коллегу) может любой администратор — крестиком в списке.

В компактных местах показывается фамилия и инициалы («Петров С.И.»), при трех и более
исполнителях хвост сворачивается в «+N»; полные имена остаются в подсказке и в блоке
«Исполнители». Инициалы собираются только если все слова похожи на части ФИО, поэтому
должность вроде «Главный администратор» не превращается в «Главный А.».

Связь хранится отдельной таблицей `assignments` (сущность ↔ пользователь ↔ момент принятия).
Имя сохраняется рядом с идентификатором: карточка останется читаемой, даже если учетную запись
потом переименуют. В отчете Excel исполнители перечисляются через запятую, а «Принят в работу» —
момент, когда сущность взяли в работу впервые.

**Редактирование.** Администратор правит любой доступный ему сигнал; автор — только свой
и только пока он не закрыт: после терминального статуса запись становится историческим
документом. Правки не переписывают карточку молча — сервер сравнивает поля со старыми
значениями и сохраняет список изменений.

**История событий** хранит полную историю действий по сигналу: создание, возвраты
на доработку и ответы подрядчика, распределение, отчеты и повторные ответы, подтверждение,
смены статуса, комментарии, правки и назначения. У каждой записи — кто и когда, комментарий и приложенные к действию файлы. У правок
дополнительно видно, что именно изменилось. Подрядчик видит ленту без внутренних записей
сотрудников (заметки кураторам, смена категории, снятие исполнителя).

**Комментарии.** Автор сигнала и сотрудники, которым он виден, переписываются прямо
в карточке: комментарий с файлами попадает в ленту и уходит письмом всем участникам.

**Фильтр «В работе»** на карте сигналов: «Все» (по умолчанию, ничего не выбрано) / «Принятые» /
«Непринятые». Фильтр уходит и в SQL-выборку отчета, а в сам отчет добавлены колонки
«Исполнитель» и «Принят в работу».

## Фоновый процесс (CRON-эмуляция)

`server/domain/escalation.js` — один таймер на всю систему: каждые 5 секунд ищет сигналы «В работе»,
у которых время в этом статусе превысило 48 часов, и переводит их в Красный от имени Системы.
Он работает независимо от того, открыт ли браузер.

## Подсистема уведомлений

**О каждом действии с сигналом** уходит письмо: создание, возврат на доработку по итогам входного
контроля, дополнения подрядчика, распределение ответственному, отчет или комментарий, направление
результата на подтверждение, подтверждение выполнения, возврат на доработку, повторная отработка,
эскалация, окончательное закрытие, отклонение, возобновление. Получатели — автор сигнала, назначенные ответственные и главный
администратор (письма входного контроля — всегда, остальные — на период тестирования, пока
`MAIL_COPY_SUPERADMIN=true`). У пользователя один общий тумблер в разделе «Аккаунт».

**Одна цепочка на сигнал.** Все письма уходят с одного адреса (`MAIL_FROM`) и с неизменной
темой `Сигнал №125. <тема>` — тема вычисляется из описания при создании и потом не меняется.
По ней Outlook собирает письма сигнала в одну переписку; заголовки `References`/`In-Reply-To`
и `Thread-Topic` помогают и другим клиентам.

**Письмо** (табличная верстка с инлайновыми стилями) содержит номер сигнала, действие и новый
статус, кто выполнил действие, комментарий, приложенные файлы и прямую ссылку в карточку сигнала.
Отправка идет в фоне: сбой доставки фиксируется в `mail_log` и не роняет саму операцию.

**Верификация почты.** При создании учетной записи выпускается одноразовый токен со сроком жизни
24 часа, на указанный адрес уходит письмо со ссылкой `/verify?token=…`. Подтверждение необязательно
и доступ не ограничивает — оно нужно для восстановления пароля.

## Файловая подсистема

- Зона Drag-and-Drop и кнопка выбора файлов в форме создания сигнала.
- Клиентская валидация: расширения `pdf, doc, docx, xls, xlsx, jpg, jpeg, png, txt` и лимит
  15 МБ на файл; отклоненные файлы перечисляются с причиной.
- Те же правила продублированы на сервере (`server/domain/files.js`) — загрузка `.exe` в обход
  интерфейса возвращает 400. MIME-тип определяется по расширению, а не по заголовку из multipart.
- Файлы кладутся в `data/uploads`, к сущности привязываются идентификаторы, отдача идет по
  `/files/:id` с `Content-Disposition: attachment` и корректным именем (RFC 5987, кириллица).
- В карточке сигнала выводится список вложений с иконкой по MIME-типу, размером и
  кнопкой скачивания.

## Экспорт в Excel

Кнопка «Экспорт в Excel» — на карте сигналов.

Клиент шлет GET-запрос `/api/export/signals?category=…&status=…&assignment=…` (ровно те фильтры,
что видны на
экране). Сервер выполняет SQL-выборку с `ORDER BY created_at DESC`, собирает книгу `.xlsx`
через ExcelJS с типизированными колонками (даты — `Date` с форматом `dd.mm.yyyy hh:mm`, счетчик
вложений — число, остальное — строки) и отдает буфер с MIME
`application/vnd.openxmlformats-officedocument.spreadsheetml.sheet` и заголовком
`Content-Disposition: attachment`. Клиент перехватывает Blob и инициирует скачивание средствами
браузера, имя файла берется из `Content-Disposition`. Обычный администратор выгружает только
доступные ему категории — ограничение накладывается в SQL, а не в интерфейсе.

## Live-режим

Сервер публикует событие изменения в SSE-канал `/api/events`, клиент в ответ перечитывает
`/api/state`. Создание сигнала, распределение по категории, ручная смена статуса, автоэскалация
и выдача категорий мгновенно отражаются во всех открытых вкладках, у всех пользователей и на
всех устройствах. При обрыве соединения в шапке загорается индикатор «офлайн», клиент
переподключается сам.

## Роли и экраны

**Гость:** `#/` — описание системы, `#/login` — вход, `#/register` — регистрация подрядчика
(название компании, ФИО, почта, пароль; название компании должно быть свободным).

**Подрядчик** (изолированная среда):
`#/new` — форма сигнала со строгой валидацией и вложениями, категорию он не выбирает;
`#/my` — личный кабинет со своими сигналами; `#/my/:id` — карточка с историей, перепиской
и текущим этапом (на входном контроле, возвращен на доработку — с комментарием, что дополнить,
ожидает подтверждения — с отчетом ответственного и кнопками «Подтвердить выполнение» /
«Вернуть на доработку»);
`#/my/:id/edit` — правка и доработка сигнала с новыми файлами. Чужие сигналы не попадают в выдачу
API, прямой запрос по чужому ID — 404.

**Администратор:**
`#/admin` — карта сигналов: колонки только по доступным категориям, фильтры и экспорт;
`#/admin/signal/:id` — карточка с историей, перепиской, вложениями, отчетом о выполнении
и кнопкой «Направить на подтверждение»;
`#/admin/verify` — экран-заглушка до подтверждения почты.

**Главный администратор** — дополнительно:
`#/admin/distribution` — раздел «Входной контроль»: новые и доработанные сигналы с кнопками
распределения и возврата на доработку, ниже — сигналы, ждущие ответа подрядчика;
`#/admin/users` — учетные записи: список администраторов с набором категорий (меняется прямо

подрядчиков. Обе страницы закрыты и guard-ом маршрута, и проверкой роли на сервере.

## Мобильный интерфейс

Мобильная раскладка добавлена так, чтобы десктопная не изменилась ни на пиксель: все правила
живут в media-запросах `max-width` (плюс блок `hover: none`) в конце `public/css/styles.css`.
Проверено замерами: на 1280×720 геометрия 12 экранов и 14 контрольных элементов совпадает
с эталоном, снятым до правок, побайтово.

Что меняется на телефоне:

- **Шапка сворачивается в бургер-меню** — 183 px → 65 px. Меню открывается по кнопке, закрывается
  тапом по пункту, тапом мимо шапки и по Escape, переживает live-перерисовку и не теряет состояние
  при обновлении данных. На экранах шире 900 px кнопки просто нет в разметке.
- **Таблицы превращаются в карточки** с подписями колонок из `data-label` (список администраторов,
  dev-инбокс) — горизонтальная прокрутка таблиц на телефоне убрана совсем.
- **Фильтры дашборда** — горизонтальные ленты вместо пяти рядов переносов, карта сигналов
  остается в пределах первого экрана.
- **Пальцевые размеры**: минимум 44 px у основных кнопок и 38 px у вспомогательных, поля формы
  16 px (иначе iOS зумит страницу при фокусе), действия по сигналу — в столбик на всю ширину.
- Учтены вырезы экрана (`env(safe-area-inset-*)`) и отключён «залипающий» hover на сенсорных экранах.

## Видео-туториал

`tutorial/signal-monitor-tutorial.mp4` — разбор всего функционала: 55 сцен, около четырех минут,
с подписью к каждому шагу и подсветкой обсуждаемого элемента. Ролик собирается скриптом, а не
записывается вручную, поэтому его можно переснять после любых изменений интерфейса:

```bash
npm i --no-save playwright-core && npx playwright install chromium
node tools/record-tutorial.mjs
```

Скрипт поднимает отдельный сервер на чистой базе (порт 5399), проходит браузером все сценарии,
рисует подписи прямо в страницу и собирает кадры в MP4 через ffmpeg. Длительность каждого кадра
задается в сценарии — текст успевают прочитать. Кадры телефона компонуются иначе: снимок слева,
подпись на свободном поле справа, иначе она не помещалась бы в узкий экран.

Почта во время записи намеренно уходит в dev-инбокс: туториал не должен рассылать настоящие
письма. Рабочая база и настройки из `.env` при записи не затрагиваются.

## Ограничения демо-реализации

- Драйвер БД — `node-sqlite3-wasm` (SQLite, собранный в WebAssembly): не требует нативной сборки,
  что важно на машинах без работающего node-gyp. Весь код работает через тонкий адаптер `sql`
  в `server/db.js`, поэтому переход на `better-sqlite3`, `node:sqlite` или PostgreSQL — правка
  одного файла.
- Пароли хешируются scrypt с индивидуальной солью, сравнение — в постоянном времени.
- Переход по ссылке подтверждения сразу открывает сессию (magic-link). Ссылка одноразовая и
  живет 24 часа; если такое поведение нежелательно, достаточно убрать `createSession`
  в `server/routes/verify.js` и оставить редирект на форму входа.
- Учетная запись подрядчика создается сразу активной: подтверждение почты требуется только
  администраторам, у которых от него зависит доступ к панели.
