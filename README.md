# Система мониторинга сигналов

Fullstack-приложение в едином фронтенд-бандле: UI-слой, слой бизнес-логики (конечный автомат
статусов, фоновый воркер эскалации) и data-слой (персистентное хранилище + live-синхронизация)
живут в одном приложении. Внешний бэкенд не требуется — роль базы играет `localStorage`,
а каналом реального времени служат события изменения хранилища.

## Запуск

```bash
node signal-monitor/server.js
```

Затем открыть адрес, который напечатает сервер (по умолчанию `http://localhost:5173`;
порт можно переопределить: `PORT=8080 node server.js`).

Приложение нужно открывать по `http://localhost`, а не двойным кликом по `index.html`:
на `file://` не работают ES-модули, события `storage` между вкладками и Web Crypto.

**Демо-доступ администратора:** `admin` / `admin123` (создается автоматически при первом запуске,
если в системе нет ни одной учетной записи администратора).

## Модель данных

**Пользователь**

| Поле | Описание |
| --- | --- |
| `id` | уникальный идентификатор; для подрядчика это ID устройства/сессии |
| `role` | `contractor` \| `admin` |
| `displayName` | отображаемое имя |
| `login`, `salt`, `passwordHash` | только у администратора |
| `createdAt` | метка времени |

Подрядчик инициализируется анонимно: при первом заходе браузеру присваивается ID устройства
(`sms:device:v1`), а запись в справочнике пользователей создается лениво — в момент первого
реального действия, то есть при создании сигнала.

**Сигнал**

| Поле | Описание |
| --- | --- |
| `id` | уникальный идентификатор |
| `authorId` | ID автора |
| `line` | `legal` \| `supply` \| `design` \| `null` (пропуск / без линии) |
| `contractorName` | название подрядчика |
| `sector` | сектор работы |
| `description` | текстовое описание |
| `status` | `yellow` \| `red` \| `green` \| `gray` |
| `createdAt`, `updatedAt` | метки времени |
| `history[]` | массив переходов: `{ at, from, to, byId, byName, byRole, note }` |

## Конечный автомат статусов

```
            (создание)
                │
                ▼
            ┌────────┐   +48 ч, только СИСТЕМА    ┌────────┐
            │ ЖЕЛТЫЙ │ ─────────────────────────► │КРАСНЫЙ │
            └────────┘                            └────────┘
              │    │                                 │   │
   автор/админ│    │только админ          автор/админ│   │только админ
              ▼    ▼                                 ▼   ▼
         ┌────────┐ ┌───────┐                 ┌────────┐ ┌───────┐
         │ЗЕЛЕНЫЙ │ │ СЕРЫЙ │                 │ЗЕЛЕНЫЙ │ │ СЕРЫЙ │
         └────────┘ └───────┘                 └────────┘ └───────┘
          терминальные статусы                 терминальные статусы
```

| Переход | Кто выполняет | Условие |
| --- | --- | --- |
| → Желтый | система | автоматически при создании сигнала |
| Желтый → Красный | **только система** | сигнал находится в Желтом статусе более 48 часов |
| Желтый/Красный → Зеленый | автор сигнала **или** любой администратор | вручную |
| Желтый/Красный → Серый | **только администратор** | вручную |

Зеленый и Серый — терминальные: любые дальнейшие переходы запрещены.
Ручное выставление Желтого и Красного запрещено на уровне автомата
(`js/domain/state-machine.js`), а не только в интерфейсе, — поэтому правило действует
и для кнопок UI, и для любого прямого вызова сервисного слоя.

## Фоновый процесс (CRON-эмуляция)

`js/domain/escalation-worker.js` каждые 5 секунд опрашивает возраст всех Желтых сигналов и по
достижении порога 48 часов переводит их в Красный, добавляя в историю запись от имени Системы.

Между вкладками выбирается один «лидер» (лок с heartbeat в `localStorage`), поэтому одно и то же
событие эскалации не записывается несколько раз. Если лидер закрыт или завис, лок протухает и его
перехватывает другая вкладка. Даже при гонке повторную запись отсекает конечный автомат: переход
Красный → Красный запрещен.

Возраст отсчитывается от момента входа в Желтый статус (запись в истории), а не от «сейчас минус
createdAt», — это остается корректным, даже если правила эволюционируют.

## Live-режим

Data-слой (`js/data/store.js`) — единственное место, знающее о физическом хранилище:

1. **Слушатель `window.addEventListener('storage', …)`** — ловит изменения из других вкладок.
2. **`BroadcastChannel`** — быстрый дублирующий канал доставки в рамках одного origin.
3. **Ревизия `rev`** — инкрементируется на каждой записи и отсекает повторную обработку
   одного и того же изменения, пришедшего по обоим каналам.
4. **Перечитывание перед записью** — `mutate()` берет актуальную версию из хранилища прямо
   перед записью, поэтому параллельная вкладка не теряет свои изменения.

Любое изменение (создание сигнала, ручная смена статуса, автоэскалация воркером) немедленно
перерисовывает шапку и активный экран во всех открытых вкладках без перезагрузки страницы.

## Роли и экраны

**Главная (`#/`)** — основное действие «Задать проблему», дополнительное «Зайти в админ аккаунт».

**Подрядчик (изолированная среда)**

- `#/new` — шаг 1: выбор линии (Юридическая / Поставка / Проектирование) или «Пропустить».
- `#/new/form` — шаг 2: Подрядчик, Сектор, Описание. Строгая клиентская валидация: при попытке
  отправки с пустыми полями сабмит блокируется, незаполненные поля подсвечиваются красным,
  под каждым выводится причина, фокус переводится на первое проблемное поле.
- `#/my` — личный кабинет: история собственных задач и их статусы; кнопка перевода активного
  сигнала (Желтый/Красный) в Зеленый.
- `#/my/:id` — карточка своего сигнала с полной историей статусов.

Подрядчики не видят ни друг друга, ни чужих сигналов: выборка идет через `listByAuthor(authorId)`,
а прямое обращение по чужому ID возвращает «Сигнал не найден» (`getForActor`).

**Администратор (глобальная среда)**

- `#/admin/login` — вход по логину и паролю.
- `#/admin` — дашборд «карта сигналов»: счетчики по статусам, фильтр по линии
  (все линии сразу либо конкретная, включая «Без линии») и дополнительный фильтр по статусу;
  сигналы разложены по колонкам-линиям и окрашены по статусу. Состояние фильтров хранится
  в query-строке, поэтому переживает live-перерисовку и остается ссылкой, которой можно поделиться.
- `#/admin/signal/:id` — детали и история любого сигнала, перевод активного сигнала
  в Зеленый или Серый. Кнопок для Желтого и Красного нет.
- `#/admin/users` — список учетных записей и создание новых администраторов.
- «Создать сигнал» — администратор может завести сигнал от своего лица по флоу подрядчика.

Маршруты администратора закрыты guard-ом: без активной сессии происходит редирект на форму входа.

## Как проверить автоэскалацию, не дожидаясь двух суток

На карточке Желтого сигнала в админ-панели есть блок «Демо-режим» с кнопкой
**«Состарить сигнал на 48 часов»**. Она сдвигает только метки времени; сам статус по-прежнему
меняет фоновый воркер — в течение ближайших пяти секунд сигнал станет Красным, а в истории
появится запись «Система · Автоэскалация: превышен порог 48 часов».

## Ограничения демо-реализации

- Хранилище — `localStorage`, то есть данные общие для вкладок одного браузера, но не между
  разными устройствами. Замена data-слоя на HTTP/WebSocket-бэкенд затрагивает только
  `js/data/store.js`: остальные слои работают с ним через `getState` / `mutate` / `subscribe`.
- Пароли хешируются SHA-256 с солью на клиенте. Для учебного стенда этого достаточно, для
  продакшена нужен серверный хеш с медленной KDF (bcrypt/argon2) и хранение вне браузера.
- Роль подрядчика определяется ID устройства: очистка данных браузера создаст нового подрядчика.
