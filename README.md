# Система мониторинга сигналов

Fullstack-приложение: Node-сервер с SQL-хранилищем (SQLite), REST API, почтовой подсистемой,
фоновым процессом эскалации и серверным экспортом в Excel — и клиент на нативных ES-модулях.
Слой предметной области (`shared/`) физически один и тот же для сервера и браузера, поэтому
статусы, правила переходов и валидация не могут разойтись между клиентом и сервером.

## Запуск

```bash
cd signal-monitor && npm install && npm start
```

Приложение поднимется на `http://localhost:5175` (порт меняется переменной `PORT`).

**Демо-доступ администратора:** `admin` / `admin123` — создается при первом запуске,
если в системе нет ни одной учетной записи.

### Почта

По умолчанию SMTP не настроен и работает **dev-инбокс**: письмо всё равно собирается настоящим
MIME-сообщением, сохраняется в `data/mailbox/*.eml` и открывается в браузере по адресу
`/dev/mailbox`. Чтобы включить реальную отправку, достаточно задать переменные окружения —
код отправки при этом не меняется:

```bash
SMTP_HOST=smtp.example.com SMTP_PORT=587 SMTP_USER=robot@example.com SMTP_PASS=... \
MAIL_FROM='Мониторинг сигналов <robot@example.com>' APP_URL=https://signals.example.com npm start
```

`APP_URL` подставляется в ссылки внутри писем (подтверждение почты, переход к карточке сигнала).
При заданном `SMTP_HOST` dev-инбокс автоматически отключается и отдает 404.

## Модель данных (SQL)

| Таблица | Назначение |
| --- | --- |
| `users` | подрядчики и администраторы; у администратора — `login`, `email` (уникальный), `password_salt`/`password_hash`, `is_email_verified`, `settings` (JSON) |
| `signals` | сигналы: автор, линия, подрядчик, сектор, описание, статус, метки времени |
| `signal_history` | история переходов: когда, из какого статуса, в какой, кем и с какой пометкой |
| `tasks` | задачи: автор, заголовок, описание, статус, метки времени |
| `files` | вложения: имя, MIME-тип, размер в байтах, URL и путь в хранилище |
| `attachments` | связь файлов с сигналом или задачей |
| `email_tokens` | одноразовые токены подтверждения почты с TTL |
| `sessions` | сессии администраторов |
| `mail_log` | журнал отправленных писем (тема, получатель, способ доставки, ошибка) |

Подрядчик инициализируется анонимно: сервер выдает браузеру куку `sms_device`, а запись в
`users` создается лениво — в момент первого реального действия (создания сигнала).

### Настройки администратора (`users.settings`)

```jsonc
{
  "notificationsEnabled": true,      // главный тумблер рассылки
  "notifyLines": "all",              // "all" либо ["legal","supply","design","none"]
  "notifyOnCreate": true,            // уведомление при создании проблемы
  "notifyOnRed": true,               // уведомление при переходе в Красный
  "notifyOnResolve": false,          // уведомление при Зеленом/Сером
  "tasksDashboardEnabled": true      // видимость модуля задач
}
```

## Конечный автомат статусов

```
            (создание)
                │
                ▼
            ┌────────┐   +48 ч, только СИСТЕМА    ┌────────┐
            │ ЖЕЛТЫЙ │ ─────────────────────────► │КРАСНЫЙ │
            └────────┘                            └────────┘
              │    │                                 │   │
   автор/админ│    │только админ          автор/админ│   │только админ
              ▼    ▼                                 ▼   ▼
         ┌────────┐ ┌───────┐                 ┌────────┐ ┌───────┐
         │ЗЕЛЕНЫЙ │ │ СЕРЫЙ │                 │ЗЕЛЕНЫЙ │ │ СЕРЫЙ │
         └────────┘ └───────┘                 └────────┘ └───────┘
          терминальные статусы                 терминальные статусы
```

| Переход | Кто выполняет | Условие |
| --- | --- | --- |
| → Желтый | система | автоматически при создании сигнала |
| Желтый → Красный | **только система** | сигнал в Желтом статусе более 48 часов |
| Желтый/Красный → Зеленый | автор **или** администратор | вручную |
| Желтый/Красный → Серый | **только администратор** | вручную |

Правила описаны в `shared/state-machine.js` и применяются на сервере до записи в БД, поэтому
запрет действует и для интерфейса, и для прямых запросов к API (проверено: ручная попытка
выставить Красный возвращает 403, подрядчик не может отклонить сигнал, терминальные статусы
не меняются).

## Фоновый процесс (CRON-эмуляция)

`server/domain/escalation.js` — один таймер на всю систему: каждые 5 секунд ищет Желтые сигналы
старше 48 часов и переводит их в Красный от имени Системы. Он работает независимо от того, открыт
ли браузер, и не требует выбора лидера между вкладками.

Чтобы увидеть эскалацию не дожидаясь двух суток, на карточке Желтого сигнала в админ-панели есть
блок «Демо-режим» с кнопкой **«Состарить сигнал на 48 часов»**: она сдвигает только метки времени,
статус по-прежнему меняет фоновый процесс.

## Подсистема уведомлений

**Верификация почты.** При создании администратора выпускается одноразовый токен со сроком жизни
24 часа, на указанный адрес уходит письмо со ссылкой `/verify?token=…`. До перехода по ссылке
доступ к панели заблокирован: и на клиенте (guard маршрутов, экран-заглушка), и на сервере
(`allSignals`, `tasks`, экспорт и API задач отдают `null`/403). Переход по ссылке помечает почту
подтвержденной и сразу открывает сессию — повторный вход не нужен. Повторный выпуск письма
доступен кнопкой на экране-заглушке; предыдущая ссылка при этом перестает работать.

**Триггеры.** Рассылку инициирует конечный автомат: функция `notificationEventFor(from, to)`
переводит переход в событие `create` / `red` / `resolve`. Никакой другой код решения об отправке
не принимает.

**Фильтрация получателей** (`server/mail/notifier.js`) — все четыре условия ТЗ:

1. `is_email_verified = 1`;
2. `settings.notificationsEnabled = true`;
3. линия сигнала входит в `settings.notifyLines` (или выбран селектор «Все»);
4. включен флаг соответствующего события (`notifyOnCreate` / `notifyOnRed` / `notifyOnResolve`).

**Письмо** формируется по HTML-шаблону (табличная верстка с инлайновыми стилями — иначе почтовые
клиенты ломают макет) и содержит ID сигнала, новый статус, линию, дату изменения, автора перехода,
подрядчика, сектор, краткое описание, список вложений и прямую ссылку на карточку сигнала.
Отправка идет в фоне: сбой доставки фиксируется в `mail_log` и не роняет саму операцию.

## Модуль «Задачи»

Независимый раздел: у задач нет таймеров, автоматических переходов и почтовых уведомлений —
только ручная смена статуса (Открыта / В работе / Завершена) в любом направлении. Визуально
дублирует дашборд сигналов: счетчики, фильтр по статусу, канбан-колонки, экспорт в Excel.

Доступ определяется флагом `tasksDashboardEnabled` в настройках конкретного администратора: при
выключении пункт меню исчезает, маршрут `#/tasks` перенаправляет в профиль, а API отвечает 403.

## Файловая подсистема

- Зона Drag-and-Drop и кнопка выбора файлов в формах создания сигнала и задачи.
- Клиентская валидация: расширения `pdf, doc, docx, xls, xlsx, jpg, jpeg, png, txt` и лимит
  15 МБ на файл; отклоненные файлы перечисляются с причиной.
- Те же правила продублированы на сервере (`server/domain/files.js`) — загрузка `.exe` в обход
  интерфейса возвращает 400. MIME-тип определяется по расширению, а не по заголовку из multipart.
- Файлы кладутся в `data/uploads`, к сущности привязываются идентификаторы, отдача идет по
  `/files/:id` с `Content-Disposition: attachment` и корректным именем (RFC 5987, кириллица).
- В карточке сигнала и задачи выводится список вложений с иконкой по MIME-типу, размером и
  кнопкой скачивания.

## Экспорт в Excel

Кнопка «Экспорт в Excel» есть на дашборде сигналов и на дашборде задач.

Клиент шлет GET-запрос `/api/export/signals?line=…&status=…` (ровно те фильтры, что видны на
экране). Сервер выполняет SQL-выборку с `ORDER BY created_at DESC`, собирает книгу `.xlsx`
через ExcelJS с типизированными колонками (даты — `Date` с форматом `dd.mm.yyyy hh:mm`, счетчик
вложений — число, остальное — строки) и отдает буфер с MIME
`application/vnd.openxmlformats-officedocument.spreadsheetml.sheet` и заголовком
`Content-Disposition: attachment`. Клиент перехватывает Blob и инициирует скачивание средствами
браузера, имя файла берется из `Content-Disposition`.

## Live-режим

Сервер публикует событие изменения в SSE-канал `/api/events`, клиент в ответ перечитывает
`/api/state`. Создание сигнала, ручная смена статуса, автоэскалация, изменение настроек и
операции с задачами мгновенно отражаются во всех открытых вкладках, у всех пользователей и на
всех устройствах. При обрыве соединения в шапке загорается индикатор «офлайн», клиент
переподключается сам.

## Роли и экраны

**Главная (`#/`)** — «Задать проблему» и «Зайти в админ аккаунт».

**Подрядчик** (изолированная среда):
`#/new` → выбор линии (или пропуск) → `#/new/form` → форма с валидацией и вложениями;
`#/my` — личный кабинет со своими сигналами; `#/my/:id` — карточка с историей и кнопкой
«Проблема решена». Чужие сигналы не попадают в выдачу API, прямой запрос по чужому ID — 404.

**Администратор** (глобальная среда):
`#/admin` — карта сигналов с фильтрами и экспортом; `#/admin/signal/:id` — карточка с историей,
вложениями и переводом в Зеленый/Серый; `#/admin/users` — список учетных записей и создание новых;
`#/admin/profile` — панель настроек уведомлений и модулей; `#/tasks` — модуль задач;
`#/admin/verify` — экран-заглушка до подтверждения почты.

## Мобильный интерфейс

Мобильная раскладка добавлена так, чтобы десктопная не изменилась ни на пиксель: все правила
живут в media-запросах `max-width` (плюс блок `hover: none`) в конце `public/css/styles.css`.
Проверено замерами: на 1280×720 геометрия 12 экранов и 14 контрольных элементов совпадает
с эталоном, снятым до правок, побайтово.

Что меняется на телефоне:

- **Шапка сворачивается в бургер-меню** — 183 px → 65 px. Меню открывается по кнопке, закрывается
  тапом по пункту, тапом мимо шапки и по Escape, переживает live-перерисовку и не теряет состояние
  при обновлении данных. На экранах шире 900 px кнопки просто нет в разметке.
- **Таблицы превращаются в карточки** с подписями колонок из `data-label` (список администраторов,
  dev-инбокс) — горизонтальная прокрутка таблиц на телефоне убрана совсем.
- **Фильтры дашборда** — горизонтальные ленты вместо пяти рядов переносов, карта сигналов
  остается в пределах первого экрана.
- **Пальцевые размеры**: минимум 44 px у основных кнопок и 38 px у вспомогательных, поля формы
  16 px (иначе iOS зумит страницу при фокусе), действия по сигналу и задаче — в столбик на всю ширину.
- Учтены вырезы экрана (`env(safe-area-inset-*)`) и отключён «залипающий» hover на сенсорных экранах.

## Ограничения демо-реализации

- Драйвер БД — `node-sqlite3-wasm` (SQLite, собранный в WebAssembly): не требует нативной сборки,
  что важно на машинах без работающего node-gyp. Весь код работает через тонкий адаптер `sql`
  в `server/db.js`, поэтому переход на `better-sqlite3`, `node:sqlite` или PostgreSQL — правка
  одного файла.
- Пароли хешируются scrypt с индивидуальной солью, сравнение — в постоянном времени.
- Переход по ссылке подтверждения сразу открывает сессию (magic-link). Ссылка одноразовая и
  живет 24 часа; если такое поведение нежелательно, достаточно убрать `createSession`
  в `server/routes/verify.js` и оставить редирект на форму входа.
- Роль подрядчика привязана к куке устройства: очистка кук создает нового подрядчика.
