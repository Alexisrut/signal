# Система мониторинга сигналов — техническая документация

Документ описывает, из чего собрана система, как она развернута на боевом
сервере и что нужно знать для ее сопровождения. Адресован технической службе,
принимающей проект.

---

## 1. Назначение

Система принимает от подрядчиков сигналы о проблемах, распределяет их по
категориям и ответственным сотрудникам, отслеживает срок решения и
автоматически повышает критичность просроченных обращений.

| Роль | Что делает |
|---|---|
| Подрядчик | создает сигналы, видит только свои, получает письма о смене статуса |
| Администратор | видит все сигналы, распределяет по категориям и людям, меняет статусы |
| Руководитель | видит сигналы своих категорий, работает с назначенными на него |
| Главный администратор | все права администратора плюс учетные записи, роли и кураторы |

Собственного кода сервера и общего слоя — около 4700 строк.

Точные версии на конкретной машине:


## 3. Архитектура

```
Браузер                     Сервер                        Хранилище
────────                    ──────                        ─────────
public/js/                  server/
  app.js       ──HTTP──►      routes/       ──►  domain/   ──►  SQLite
  ui/views/    ◄─JSON───      api.js             signals.js     (файл .db)
  data/store.js                files.js          users.js
       ▲                       export.js         files.js       Диск
       │                                                        uploads/
       └────SSE────           events.js
                              mail/       ──SMTP──►  почтовый сервер

              shared/  ← один и тот же код у сервера и браузера
                constants.js      статусы, роли, категории, лимиты
                state-machine.js  правила переходов и прав
                validation.js     проверки форм
```

### Общий слой предметной области

Каталог `shared/` физически один и тот же для сервера и браузера: сервер
импортирует его как ESM-модули, браузер получает по адресу `/shared/...`.
Следствие — правила переходов статусов, набор ролей и валидация **не могут
разойтись** между клиентом и сервером. Проверка на клиенте существует для
удобства пользователя, решение принимает сервер.

### Клиент

Одностраничное приложение на хеш-роутере (`public/js/ui/router.js`).
Каждое представление реализует три функции: `render` (строит разметку),
`mount` (навешивает обработчики), `cleanup` (снимает их). Состояние держится
в одном месте — `public/js/data/store.js`, — и представления на него
подписываются.

### Сервер

`server/index.js` — таблица маршрутов, отдача статики, единая обработка ошибок.
Бизнес-логика вынесена в `server/domain/`, доступ к данным — тонкая обертка
`sql` над WASM-сборкой SQLite с позиционными параметрами `?`.

Параметризованы **все** запросы без исключения — конкатенации значений в SQL
в коде нет.

| Параметр | Значение |
|---|---|
| Адрес сайта | https://signal.vis.ru |
| DNS | A-запись `signal.vis.ru → 195.133.238.10` |
| Сертификат | wildcard, SAN: `*.vis.ru`, `vis.ru` |
| Удостоверяющий центр | GlobalSign GCC R3 DV TLS CA 2020 |

`fullchain.pem` содержит сертификат домена, следом промежуточный
`GlobalSign GCC R3 DV TLS CA 2020` и корневой `GlobalSign Root CA - R3`.
Порядок обязателен: лист первым. При обратном порядке nginx стартует, но
Android и старые Java-клиенты отвергают цепочку, тогда как десктопный Chrome
принимает — ошибку легко не заметить.

### Схема прохождения запроса

```
Клиент ──443/TLS──► nginx ──HTTP──► 127.0.0.1:5175 ──► приложение
                      └──────────► /var/www/guides (руководства, напрямую)
```

TLS обрывается на nginx. Порт приложения закрыт снаружи и слушает только
петлевой интерфейс. Адрес клиента передается заголовком `X-Forwarded-For`
(включено `TRUST_PROXY=true`).

## 6. Схема данных

Файл базы: `/var/lib/signal-monitor/signal-monitor.db`.
Миграции применяются автоматически при старте (`migrate()` в `server/db.js`),
отдельной команды не требуется.

| Таблица | Назначение |
|---|---|
| `users` | учетные записи всех ролей |
| `signals` | сигналы |
| `signal_history` | лента событий по сигналу |
| `signal_views` | отметки «просмотрено» для счетчиков непрочитанного |
| `assignments` | назначение людей на сущность |
| `files` | загруженные файлы |
| `attachments` | связь файлов с сущностями |
| `sessions` | сессии входа |
| `email_tokens` | токены подтверждения почты и сброса пароля |
| `mail_log` | журнал отправленных писем |

### Ключевые поля

**`users`** — `role`, `login` (уникален), `email` (уникален),
`password_salt` + `password_hash`, `is_email_verified`, `categories` (JSON,
курируемые категории руководителя), `notify` (JSON, настройки уведомлений),
`has_own_signals` (залипающий флаг: вкладка «Мои сигналы» появляется с первым
сигналом и больше не исчезает).

**`signals`** — `author_id`, `category`, `contractor_name`, `sector`,
`description`, `status`, `distributed_at`, `closed_at`, `paused_ms`
(накопленное время в закрытом состоянии — вычитается при возобновлении, чтобы
таймер не доначислял простой), `assignment_note` (заметка ответственным,
подрядчику не видна).

**`signal_history`** — `kind` (`create`, `status`, `note`, `reopen`),
`status_from`, `status_to`, `by_id`, `by_name`, `by_role`, `note`, `details`.

**`files`** — `storage_path` (путь на диске), `uploaded_by` (кто загрузил —
на этом строится проверка прав).

Хранилище файлов: `/var/lib/signal-monitor/uploads`, имена на диске
обезличены, оригинальное имя лежит в базе.

## 7. Предметная модель

### Статусы

| Статус | Смысл |
|---|---|
| `yellow` | сигнал открыт, в пределах срока |
| `red` | критичный: просрочен или переведен вручную |
| `green` | решен |
| `gray` | отклонен / закрыт без решения |

### Разрешенные переходы

Описаны декларативно в `shared/state-machine.js` и применяются на сервере
**до** записи в базу.

| Переход | Кто может |
|---|---|
| `yellow → red` | система (автоэскалация) или администратор вручную |
| `yellow`/`red` → `green` | автор сигнала или любой администратор |
| `yellow`/`red` → `gray` | администратор |
| `green`/`gray` → открытый | возобновление; накопленная пауза пишется в `paused_ms` |

**Автоэскалация:** порог 48 часов с момента создания. Фоновый процесс
(`server/domain/escalation.js`) запускается вместе с сервером и переводит
просроченные желтые сигналы в красные от имени системной роли. Время в
закрытом состоянии в срок не засчитывается.

### Категории

`Административный/финансовый`, `Проектирование`, `Поставка`, `Разное`.
Сигнал создается нераспределенным; категорию назначает администратор.
Руководителю доступны только сигналы курируемых им категорий.

### Ограничения предметной области

| Параметр | Значение |
|---|---|
| Порог эскалации | 48 часов |
| Срок жизни сессии | 7 суток |
| Срок жизни токена сброса пароля | 1 час |
| Максимальный размер файла | 15 МБ |
| Файлов за один запрос | 10 |
| Разрешенные расширения | `pdf`, `doc`, `docx`, `xls`, `xlsx`, `txt`, `jpg`, `jpeg`, `png` — ровно девять |

## 8. HTTP API

Все ответы — JSON. Идентификация по куке сессии, отдельных токенов нет.

### Состояние и сессия

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/state` | полный снимок состояния под права текущего пользователя |
| GET | `/api/whoami` | текущий пользователь |
| GET | `/api/events` | поток изменений (SSE), только для вошедших |

### Сигналы

`POST /api/signals` · `GET|PUT /api/signals/:id` ·
`POST /api/signals/:id/status` · `/reopen` · `/assign` · `/assignees` ·
`/seen` · `/category`

### Аутентификация

`POST /api/auth/login` · `/logout` · `/register` · `/forgot` · `/password` ·
`GET|POST /api/auth/reset`

### Пользователи

`POST /api/admins` · `PUT /api/users/:id/categories` · `PUT /api/users/:id/role` ·
`DELETE /api/users/:id` · `PUT /api/notifications` · `POST /api/verification/resend`

### Файлы и выгрузка

`POST /api/files` · `GET /files/:id` · `GET /api/export/signals`

### Служебные

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/verify` | подтверждение почты по ссылке из письма |
| GET | `/reset` | переброс токена сброса в хеш-маршрут приложения |

Неизвестный путь без расширения отдает оболочку приложения (SPA-фолбэк).
Путь **с** расширением честно отвечает 404 — иначе пропавший `.js` вернулся бы
как HTML со статусом 200, браузер молча отверг бы модуль по MIME-типу, и
вместо ошибки была бы пустая страница.

## 9. Живое обновление

Сервер публикует изменения в поток `text/event-stream` по адресу
`/api/events`. Клиент в ответ перечитывает `/api/state`.

**Наружу уходит только номер ревизии:**

```
event: change
data: {"rev":42}
```

Идентификаторы сигналов, статусы и категории в поток не попадают: канал общий
для всех подключенных, и подрядчик получал бы в нем сводку по чужим сигналам.
Клиенту достаточно знать «что-то изменилось» — дальше он запрашивает состояние,
отфильтрованное под его права.

Поток открыт только вошедшим, гостю сервер отвечает 401. Раз в 25 секунд уходит
комментарий-пинг, чтобы прокси не закрыл молчащее соединение. В nginx для этого
маршрута отключена буферизация и поднят таймаут ответа до часа.

## 10. Почта

Отправка через SMTP. Порт 465 — SSL с первого байта, 587 — STARTTLS; при 587
выставляется `requireTLS`, поэтому открытым текстом письма не уйдут даже если
сервер не предложит шифрование.

Если `SMTP_HOST` не задан, приложение переходит в режим dev-инбокса: письма
складываются на диск в формате `.eml`. На бою этот режим не используется, его
страница закрыта для всех, кроме главного администратора.

| Событие | Сотрудникам | Автору-подрядчику |
|---|---|---|
| Новый сигнал в системе | да | нет |
| Сигнал стал критичным | да | да |
| Сигнал закрыт | да | да |
| Сигнал возобновлен | да | да |

У сотрудника есть общий тумблер и выбор событий. У подрядчика выбора нет:
только общий тумблер, и письма приходят исключительно о смене статуса его
собственных сигналов. Письмо о создании автору не отправляется намеренно.

Рассылка идет в фоне и не задерживает HTTP-ответ: ошибка доставки попадает
в `mail_log`, но не срывает саму операцию со статусом.

## 11. Безопасность

### Аутентификация и сессии

- Пароли хранятся как `scrypt`-хеш с индивидуальной солью. Открытых паролей
  в базе нет.
- Сессия — случайный токен в куке `sms_session` со сроком 7 суток.
- Флаги куки: `HttpOnly`, `SameSite=Lax`, `Secure`.
- Просроченные сессии и токены чистятся при старте и далее раз в час.

### Ограничение частоты запросов

Реализовано в `server/ratelimit.js`, ключ — действие плюс адрес клиента.

| Действие | Лимит |
|---|---|
| Вход | 10 попыток / 15 минут |
| Регистрация | 5 / час |
| Отправка писем | 5 / час |
| Создание сигналов | 60 / час |
| Загрузка файлов | 60 / час |

При превышении — 429 с заголовком `Retry-After`. Успешный вход обнуляет счетчик.

Без этого пароль администратора подбирался бы в один поток, а сервер заваливался
одним скриптом: проверка каждого пароля через `scrypt` расходует процессорное
время.

### Заголовки безопасности

Ставятся приложением (`setSecurityHeaders` в `server/http.js`) до маршрутизации,
поэтому попадают в любой ответ, включая ошибки и статику. В nginx они
намеренно **не** дублируются — кроме блока `/guides/`, который до приложения
не доходит и получает их от nginx.

| Заголовок | Значение |
|---|---|
| `Content-Security-Policy` | `default-src 'self'`, `object-src 'none'`, `frame-ancestors 'none'`, `base-uri 'self'`, `form-action 'self'` |
| `Strict-Transport-Security` | `max-age=31536000; includeSubDomains` |
| `X-Frame-Options` | `DENY` |
| `X-Content-Type-Options` | `nosniff` |
| `Referrer-Policy` | `same-origin` |
| `Cross-Origin-Opener-Policy` | `same-origin` |
| `Cross-Origin-Resource-Policy` | `same-origin` |
| `Permissions-Policy` | `geolocation=(), microphone=(), camera=(), interest-cohort=()` |

HSTS и флаг `Secure` включаются автоматически, когда `APP_URL` начинается
с `https://`.

### Разграничение доступа

Права проверяются **на сервере** для каждого запроса. Проверки на клиенте
существуют для удобства и защитой не считаются.

- **Подрядчик** видит только свои сигналы. Ответ API для него дополнительно
  фильтруется (`forContractor` в `server/domain/signals.js`): заметка
  ответственным обнуляется, из ленты событий остаются только системные записи
  о смене статуса, поля сокращаются до времени, вида и статусов — имена и роли
  сотрудников не передаются даже в сыром JSON.
- **Руководитель** ограничен курируемыми категориями.
- **Кураторство и смену ролей** ведет только главный администратор. Смена роли
  разрешена строго между «Администратор» и «Главный администратор».

### Файлы

- Загрузка требует сессии.
- Проверяются расширение (белый список), размер (15 МБ) и количество (10).
- **Право на файл выводится из права на сигнал**, к которому он приложен, а не
  из знания ссылки. Посторонний получает 404, а не 403 — по коду ответа нельзя
  установить, существует ли файл.
- Прикрепить к своему сигналу можно только собственную загрузку.

### Прочее

- Отдача статики защищена от выхода за корень каталога (path traversal).
- Тексты внутренних сбоев наружу не уходят — клиент получает обобщенное
  «Внутренняя ошибка сервера», подробности остаются в журнале.
- Данные, попадающие в HTML страницы подтверждения почты, экранируются.
- Порт приложения закрыт снаружи, доступ только через nginx с TLS.

### История проверки

Перед выкаткой проведен аудит с воспроизведением атак на работающем сервере.
Найденные и закрытые дыры: анонимная загрузка файлов, анонимное скачивание
любого вложения, открытый наружу поток событий, отсутствие ограничения на
подбор пароля, утечка служебных данных подрядчику через API, отсутствие
защитных заголовков, кука без флага `Secure`. Все исправления перепроверены
теми же пробами.

## 12. Эксплуатация

### Выкатка новой версии

**Источник правды — git. Править файлы на сервере вручную нельзя:** при
следующем обновлении правки либо потеряются, либо встанут конфликтом посреди
выкатки.

Порядок: изменения коммитятся и отправляются на GitHub, затем с рабочей машины
выполняется одна команда:

```bash
ssh -t -p 2626 visuser@195.133.238.10 'cd signal-monitor && ./deploy/deploy.sh'
```

Скрипт `deploy/deploy.sh`:

1. отказывается работать, если в рабочем каталоге есть правки мимо git;
2. показывает, какие коммиты приедут, и сводку изменений;
3. предупреждает отдельно, если изменился `package-lock.json` (реестр npm
   с сервера недоступен) или конфиг nginx (его нужно применить вручную);
4. запоминает текущий коммит, перематывает код, перезапускает службу;
5. проверяет, что приложение отвечает 200, и при неудаче показывает журнал.

Посмотреть, что приедет, ничего не меняя — `./deploy/deploy.sh --dry-run`.
Вернуться на предыдущую версию — `./deploy/deploy.sh --rollback`.

Вне git живут три вещи, деплой их не трогает: `.env` (пароли), конфиг nginx
в `/etc/nginx/` (эталон — `deploy/nginx-signal.vis.ru.conf`, о расхождении
скрипт предупреждает) и руководства в `/var/www/guides` (исходник — каталог
`guides/` в репозитории).

### Управление службой

```bash
sudo systemctl status signal-monitor
sudo systemctl restart signal-monitor
journalctl -u signal-monitor -f
journalctl -u signal-monitor -n 50 --no-pager
```

Юнит: `/etc/systemd/system/signal-monitor.service`. Настроен `Restart=always`
с паузой 5 секунд — приложение поднимается само после сбоя и после перезагрузки
сервера. Процесс заперт средствами systemd: `ProtectSystem=strict`,
`ProtectHome=read-only`, `NoNewPrivileges`, `PrivateTmp`. Единственный каталог,
доступный ему на запись, — `/var/lib/signal-monitor`.

### Диагностика при старте

Приложение печатает сводку и предупреждает о небезопасных настройках:

```
Система мониторинга сигналов → https://signal.vis.ru
Слушает: 127.0.0.1:5175 (только петля — наружу через обратный прокси)
Почта: реальная отправка через SMTP
Автоэскалация: порог 48 ч, фоновый процесс запущен
```

Любая строка `ВНИМАНИЕ` требует внимания: `APP_URL` без https, выключенный
`TRUST_PROXY` за прокси, открытый наружу порт или пароль администратора
по умолчанию.

### nginx

```bash
sudo nginx -t
sudo systemctl reload nginx
```

Конфигурация: `/etc/nginx/sites-available/signal.vis.ru`, эталон —
`deploy/nginx-signal.vis.ru.conf`.

| Параметр | Значение | Зачем |
|---|---|---|
| `client_max_body_size` | 160m | 10 вложений по 15 МБ за один запрос |
| `proxy_buffering off` для `/api/events` | — | иначе поток изменений копится в буфере и интерфейс показывает «офлайн» |
| `proxy_read_timeout 1h` для `/api/events` | — | поток держится открытым часами |
| `proxy_read_timeout 120s` для остального | — | выгрузка Excel на большой базе собирается не мгновенно |
| `location /guides/` | `root /var/www` | руководства отдаются напрямую, минуя приложение |

### Локальный запуск

```bash
./run.sh              # обычный запуск
./run.sh --dev-mail   # письма не отправляются, складываются в data/mailbox
PORT=5180 ./run.sh    # другой порт
```

Скрипт проверяет версию Node, целостность `node_modules`, наличие `.env` и
занятость порта, и предупреждает, если настроен реальный SMTP — иначе локальные
опыты разошлют письма живым адресатам.

### Резервное копирование

Базу SQLite **нельзя** копировать через `cp` на работающем сервере — получится
поврежденный файл. Нужен `.backup`:

```bash
sqlite3 /var/lib/signal-monitor/signal-monitor.db \
  ".backup '/var/lib/signal-monitor/backup-$(date +%F).db'"
```

Вложения лежат обычными файлами в `/var/lib/signal-monitor/uploads` —
забираются `rsync`-ом. Рекомендуемое расписание — ежедневно ночью, с хранением
14 копий (готовая строка для cron есть в `deploy/README.md`).

### Зависимости

Обычный путь — `npm ci --omit=dev`. **Особенность этого сервера:** с него
недоступен реестр `registry.npmjs.org`, соединение зависает и обрывается по
таймауту. При развертывании дерево собиралось на рабочей машине и переносилось
файлом. Нативных сборок в дереве нет, поэтому перенос корректен:

```bash
# на рабочей машине, из корня проекта
npm ci --omit=dev && tar -czf node_modules.tar.gz node_modules
scp -P 2626 node_modules.tar.gz visuser@195.133.238.10:/home/visuser/signal-monitor/
# на сервере
cd /home/visuser/signal-monitor && rm -rf node_modules \
  && tar -xzf node_modules.tar.gz && rm node_modules.tar.gz \
  && npm ls --omit=dev --depth=0
```

Проверка успеха — четыре строки без пометок `UNMET DEPENDENCY` и `extraneous`.
Считать каталоги в `node_modules` бесполезно: осиротевшие пакеты от неудачной
установки занимают место недостающих, и число сходится при сломанном дереве.

### Замена сертификата

```bash
sudo cp fullchain.pem /etc/ssl/vis.ru/fullchain.pem
sudo cp privkey.pem   /etc/ssl/vis.ru/privkey.pem
sudo chown root:root /etc/ssl/vis.ru/*
sudo chmod 644 /etc/ssl/vis.ru/fullchain.pem
sudo chmod 600 /etc/ssl/vis.ru/privkey.pem
sudo nginx -t && sudo systemctl reload nginx
```

Проверки перед перезагрузкой конфигурации. Ключ должен подходить к сертификату,
две строки обязаны совпасть:

```bash
sudo openssl x509 -in /etc/ssl/vis.ru/fullchain.pem -noout -pubkey | openssl sha256
sudo openssl pkey -in /etc/ssl/vis.ru/privkey.pem -pubout | openssl sha256
```

Порядок сертификатов в файле — лист первым, следом промежуточные:

```bash
sudo openssl crl2pkcs7 -nocrl -certfile /etc/ssl/vis.ru/fullchain.pem \
  | openssl pkcs7 -print_certs -noout | grep ^subject
```

Важно: `openssl x509 -in файл` читает **только первый** сертификат. В файле
из нескольких сертификатов это дает отпечаток не того ключа — типичный источник
ложной тревоги «ключ не подходит».

## 14. Диагностика типовых проблем

| Симптом | Причина и где смотреть |
|---|---|
| 502 от nginx | приложение не поднялось: `systemctl status signal-monitor`, `journalctl -u signal-monitor -n 50` |
| Значок «офлайн» в интерфейсе | поток `/api/events` буферизуется — проверить `proxy_buffering off` |
| 413 при загрузке файла | `client_max_body_size` в конфиге nginx |
| Вход блокируется сразу у всех | не задан `TRUST_PROXY=true` — все клиенты считаются одним адресом |
| Письма не уходят | `journalctl -u signal-monitor \| grep -i smtp` |
| Кука приходит без `Secure` | `APP_URL` не начинается с `https://` |
| `Cannot find module ...` при старте | неполное дерево `node_modules`, см. раздел 12 |
| `EADDRINUSE` при ручном запуске | приложение уже работает под systemd — смотреть журнал, а не запускать вторую копию |
| Браузер ругается на сертификат | истек срок либо нарушен порядок в `fullchain.pem`, см. раздел 13 |
| `nginx: unknown directive "http2"` | конфиг из более новой версии nginx; на этой сборке параметр задается внутри `listen` |
| `deploy.sh` отказывается работать | на сервере есть правки мимо git — перенести их в репозиторий или отбросить |

## 15. Известные ограничения и сознательные решения

**Один экземпляр приложения.** Счетчики ограничения частоты живут в памяти
процесса, подписки на поток изменений — тоже, база SQLite допускает одного
пишущего. Горизонтальное масштабирование потребует вынести счетчики и шину
событий во внешнее хранилище и сменить СУБД. Для текущей нагрузки — десятки
пользователей, сотни сигналов — этого с запасом достаточно.

**Перезапуск обнуляет счетчики попыток входа.** Осознанный размен простоты
на строгость.

**Проверка пароля блокирует цикл событий** на несколько миллисекунд: `scrypt`
вызывается синхронно. Практическую атаку закрывает ограничение частоты; полное
решение — перевод на асинхронный вызов — затрагивает пять функций работы
с паролями и не выполнялось.

**CSP разрешает инлайновые скрипты** (`script-src 'self' 'unsafe-inline'`).
В `index.html` их два: установка темы до отрисовки (иначе страница мигает
светлым) и сторож загрузки, который обязан сработать, даже когда основной
модуль не загрузился. Остальные директивы CSP действуют в полную силу.

**Регистрация подрядчиков открыта.** Это модель работы системы, а не упущение.
Ограничена пятью регистрациями в час с одного адреса.

**Руководства в `/guides/` общедоступны** — без входа, по прямой ссылке.
Закрытие их за авторизацией потребует работы в коде приложения.

**Реестр npm недоступен с сервера.** Ограничение сети, обходится переносом
дерева зависимостей файлом (раздел 12).

**Продление сертификата ручное.** Автоматического обновления (ACME) нет:
используется корпоративный wildcard, выдаваемый владельцем домена.
